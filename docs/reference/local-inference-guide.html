01What inference actually is

A large language model is, at its core, a very large mathematical function. You feed it a sequence of tokens (words or word-fragments encoded as integers), and it produces a probability distribution over what the next token should be. Inference is the act of running that function — repeatedly — to generate text.

Three terms you'll see everywhere:

  • Weights — the learned parameters of the model. For a 7-billion-parameter model, that's 7 billion floating-point numbers. These are fixed after training; inference never changes them (fine-tuning does, but that's a different activity).
  • Token — a chunk of text. Common words are one token, rare words get split into pieces. Roughly 0.75 words per token for English, so ~750 tokens ≈ 500 words.
  • Forward pass — one evaluation of the model. Feed in a sequence, get out a prediction for the next token.

The surprising fact: generation is a loop

LLMs generate one token at a time. To write a 500-word answer, the model runs its forward pass ~670 times in a row, each time appending the newly chosen token to the input and predicting the next one:

Input: "The capital of France is" Run 1: "The capital of France is Paris" Run 2: "The capital of France is Paris ." Run 3: "The capital of France is Paris. \n" ...repeat hundreds of times...

This single fact — generation is sequential, one token at a time, and each step depends on all previous ones — drives nearly every performance characteristic of local inference. You cannot parallelize the generation of one response, because token 42 depends on token 41.

Why this matters

ChatGPT's speed feels "fast enough" because thousands of users' requests are batched together on datacenter GPUs, keeping the hardware busy. On your Mac, you're the only user, so the hardware is massively underutilized during decode. Almost all local-inference optimization is about accepting this and optimizing the sequential loop itself.

02Prefill vs decode — the two phases

Inference has two completely different phases, with different bottlenecks. Confusing them is the #1 source of benchmark confusion.

Prefill (processing your prompt)

When you hit enter, the model processes your entire prompt at once. These tokens can be processed in parallel — the computation for token 5 doesn't need token 6's output. This makes prefill compute-bound: the GPU does huge batches of matrix multiplications and actually gets to use its raw FLOPS.

Prefill speed is measured in tokens/second of input processing, and it's usually very fast — hundreds to thousands of tok/s. It's also called time-to-first-token (TTFT) from the user's perspective: the pause before the first word appears.

Decode (generating the response)

After prefill, the model generates its own output one token at a time. Each step processes a single token through all the layers. One token = one row-vector × huge weight matrices. This makes decode memory-bandwidth-bound, not compute-bound.

The single most important asymmetry

Prefill: GPU does math at full tilt, bandwidth idle. Decode: GPU streams weights from memory, math units mostly idle. They are different workloads wearing one API's trenchcoat. Optimizations that help one can hurt the other — e.g. heavy quantization barely hurts prefill (compute-bound anyway) but directly speeds decode (less to stream).

Why decode is memory-bound (the roofline intuition)

To produce one token, the GPU must read every weight in the model once. For each weight it does roughly one multiply-accumulate operation. That's a terrible arithmetic-to-bytes ratio — 1 operation per 2 bytes (at 4-bit quantization) or 1 per 4 bytes (8-bit). GPUs are built for the opposite: thousands of operations per byte.

The consequence:

decode speed ≈ memory bandwidth ÷ bytes of weights read per token Example: M4 Max, ~546 GB/s bandwidth 8B model at 4-bit ≈ 4.8 GB of weights 546 / 4.8 ≈ 113 tok/s ← theoretical ceiling Real runtimes: 60–85 tok/s ← 60–75% of ceiling

That's the whole game. Your Mac's decode speed is essentially "how fast can I stream the weights through the memory system." A 70B model is ~40GB at 4-bit, so the same M4 Max gives ~13 tok/s. The model size in GB is the speed, divided by bandwidth.

Rule of thumb: tok/s ≈ (unified memory bandwidth in GB/s) ÷ (model size in GB, including KV overhead). Memorize this. It predicts performance better than any marketing claim.

03The transformer forward pass

What actually happens to a token inside the model? A modern decoder-only transformer (GPT, Llama, Qwen, Mistral — they're all variations) does this:

token → [embedding lookup] one row of a big table → for each of N layers (e.g. 32): → [RMSNorm] → [attention]: "what have I seen so far that matters?" → [RMSNorm] → [MLP / feed-forward]: "think about it locally" → [final norm] → [output head] projects to vocabulary → logits → probabilities

Attention: the token reads its history

Attention lets the current token "look back" at every token before it and decide which ones are relevant. Mechanically: the token is converted into a query vector, which is compared against key vectors stored for every previous token. The result is a weighted mix of their value vectors. This is where "the model remembers your conversation" lives.

Three vectors per token per layer — query (Q), key (K), value (V) — are the machinery. The K and V vectors of past tokens must be stored (that's the KV cache, chapter 5).

The MLP: where most parameters live

After attention, each token passes through a feed-forward network — two large matrix multiplications with an activation function between. Here's the budget shocker:

Where the parameters actually are (7B model example)

ComponentShare of paramsWhat it does
MLP layers (all 32)~66%Per-token "thinking"
Attention projections~8%Q/K/V/O matrices
Embedding + output head~26%Vocabulary mapping

Two-thirds of the model is MLP, and the whole thing gets streamed from memory every single token. That's why model size in GB predicts speed so directly.

Grouped-query attention (GQA)

Modern models use fewer key/value heads than query heads (e.g. 8 KV heads for 32 query heads). This was invented specifically to shrink the KV cache — it's why a 7B model from 2024 uses ~4x less cache memory than GPT-2-style attention would. When comparing models for local use, KV-head count is a quiet spec that hugely affects long-context performance.

04The arithmetic of speed — what limits your Mac

Three limits, in order of which bites first:

1. Memory bandwidth (dominant during decode)

As established in chapter 2. Per-M-series-chip unified memory bandwidth:

ChipBandwidth8B 4-bit decode ceiling
M1 / M2 (base)~100 GB/s~20 tok/s
M2 / M3 Pro~150–200 GB/s~30–40 tok/s
M3 Max~400 GB/s~80 tok/s
M4 Max~546 GB/s~110 tok/s
M5 (base, per Apple's claims)~150+ GB/s~30 tok/s

Note that this is a ceiling — real engines hit 60–75% of it because of kernel overheads, cache pollution, and non-ideal memory access patterns. Closing that gap is chapter 18's territory.

2. Compute FLOPS (dominant during prefill & training)

Prefill and batched inference hit the GPU's math units. Apple GPUs are strong here — an M4 Max does on the order of 30–40 TFLOPS (fp16). During decode, nearly all of this goes unused, which is precisely the slack speculative decoding exploits (chapter 11).

3. Memory capacity (limits which model you can run at all)

Unified memory is shared between the OS, apps, GPU, and model. Practical rule: you can run a model if

model GB (at your quant) + KV cache GB + ~8 GB (system+apps) ≤ total RAM KV cache size = 2 × layers × kv_heads × head_dim × context × bytes (2 = K and V; bytes ≈ 0.5–1.0 with quantized cache) Example: Llama-3.1-8B, 32 layers, 8 kv heads, fp16 cache, 32k context: 2 × 32 × 8 × 128 × 32768 × 2 B ≈ 4.3 GB

The 32GB vs 128GB question, answered by one number

A 70B model at 4-bit needs ~40GB of weights. On a 32GB Mac: impossible. On a 128GB Mac: runs at ~10 tok/s with room for context. Capacity buys capability, bandwidth buys speed, and you can't trade one for the other.

4. Thermal/power reality

MacBooks sustain far lower power than desktop GPUs (a laptop M-Max chip sustains maybe 60–80W under GPU load vs 300–450W for an RTX 4090). Sustained long generations can throttle slightly, and fans matter. For single-user decode this rarely matters (you're bandwidth-bound, not compute-bound), but long prefill jobs (RAG over huge documents) can thermal-trim on laptops.

05The KV cache — inference's hidden organ

Every token generated so far must keep its K and V vectors alive so future tokens can attend to it. That storage is the KV cache, and it is the second-largest consumer of memory after the weights — and during decode it's read alongside the weights every single step, so it eats the same precious bandwidth.

Why it grows quadratically-ish

Cache size is proportional to context length × layers × kv_heads × head_dim. Double the context, double the cache. And the cost of attention itself grows with context too: each new token must compare against all stored ones.

The techniques built around it

  • Cache quantization — store K/V at 8-bit or even 4-bit instead of 16-bit. Nearly all runtimes support this; it halves/quarters cache memory with minimal quality loss. Flag names: -ctk q8_0 -ctv q8_0 in llama.cpp, kv_bits in MLX.
  • Prefix caching — if the start of your prompt is the same across calls (system prompt, pasted documents, an agent's transcript), the cache for that prefix can be reused instead of recomputed. This collapses TTFT dramatically — vllm-mlx measured 5.8x TTFT improvement on cache hits. This is why agent frameworks that "append to the same conversation" get faster over time.
  • Sliding-window attention — some models (Mistral-family) only attend to the last N tokens at some layers, bounding cache size permanently.
  • Cache eviction / paged attention — manage cache in fixed-size pages so it can grow without fragmentation, and evict cold pages under memory pressure (vLLM's invention, ported to Mac in vllm-mlx).

The context-length trap

A model advertised at "128k context" will often exceed your available memory at that length once the KV cache is included, and even if it fits, attention cost grows and decode slows. The honest usable context is: what fits in RAM after weights and OS, at a speed you tolerate.

06Apple Silicon anatomy

An M-series chip is a system on a chip: CPU cores, GPU cores, memory controller, neural engine, caches — all one die, sharing one pool of RAM.

┌─────────────────────────────────────────────────┐ │ M4 Max SoC │ │ │ │ ┌──────────┐ ┌───────────────┐ ┌──────────┐ │ │ │ CPU │ │ GPU │ │ Neural │ │ │ │ 12 cores │ │ 40 cores │ │ Engine │ │ │ │ P + E │ │ (SIMD units) │ │ (AMX/AE) │ │ │ └────┬─────┘ └───────┬───────┘ └──────────┘ │ │ │ │ │ │ ┌────┴────────────────┴─────────────────────┐ │ │ │ SLC (system-level cache) │ │ │ ├────────────────────────────────────────────┤ │ │ │ Memory controller │ │ │ └────────────────────┬───────────────────────┘ │ │ │ unified bus │ │ ┌────────┴────────┐ │ │ │ LPDDR5 RAM │ ← single pool │ │ │ (e.g. 128GB) │ │ │ └─────────────────┘ │ └─────────────────────────────────────────────────┘

The parts that matter for LLM inference

  • The GPU does essentially all LLM math. Apple GPUs are tile-based, unified-memory designs — great at streaming large matrices from RAM, weaker at raw FP32 compute vs NVIDIA, but for bandwidth-bound decode that's irrelevant.
  • The Neural Engine (ANE) is a separate accelerator. It's extremely fast for fixed-shape workloads (Core ML apps) but historically awkward for LLMs because generation has dynamic shapes and needs a live KV cache. Apple's own on-device Apple Intelligence models run on ANE, but open toolchains don't really support it. As of 2026: ignore ANE for local LLMs.
  • The memory controller is the star. Bandwidth numbers in chapter 4 are what your decode speed literally is.

Why the chip generations matter less than you'd think

M1 → M4 improved compute a lot, but bandwidth much less (100 → 546 GB/s across the Max tier, and base chips went 68 → 120 GB/s). Since decode is bandwidth-bound, an M1 Max (400 GB/s) still runs a 7B model at speeds competitive with a base M4. Bandwidth tier (Base/Pro/Max/Ultra) predicts local LLM performance far better than chip generation.

07Unified memory — the Mac's unfair advantage

On a PC with a discrete GPU, the model lives in system RAM and must be copied into VRAM; VRAM capacity (8–24GB consumer) is a hard wall. On a Mac, CPU and GPU address the same physical memory with no copy step. Consequences:

  • The GPU can use nearly all your RAM. A 128GB Mac is a 96GB+ "GPU". No consumer card approaches that.
  • Zero-copy loads. A memory-mapped model file becomes GPU-visible with no import step — instant startup, and models can be loaded on demand.
  • One shared bus to optimize. The whole engineering game (chapters 14–18) is saturating this one bus.

The catch

Bandwidth is shared with everything else. A browser churning in the background measurably slows decode. Chrome using 20GB of your 64GB steals both capacity and bandwidth. Serious local-inference setups close their apps. Also, macOS historically wired a fraction of RAM for wired (non-pageable) GPU allocations; modern MLX/llama.cpp manage `iogpu.wired_limit` or equivalent to reclaim most of it — but leave headroom or the system will thrash and kill performance.

Practical memory budget: total RAM − 10GB (system) − your apps = usable model+cache budget. 32GB Mac → ~20GB budget (8B/14B class). 64GB → ~50GB (35B MoE, 30B dense). 128GB → ~110GB (70B dense, 100B+ MoE).

08Metal & GPU compute on macOS

Metal is Apple's GPU API — the layer between high-level runtimes (MLX, llama.cpp's backends) and the silicon. Understanding its shape explains where engine overheads come from:

  • Command buffers & encoders — work is recorded into buffers and submitted to the GPU. Each recorded shader call has CPU-side overhead; hundreds of small kernels per token (as naive implementations produce) spend real time on launch overhead rather than math. Fusion (merging ops into fewer kernels) is a top optimization for exactly this reason.
  • Shader compilation — Metal shaders compile to GPU code at runtime, with a small stutter on first use. Engines cache compiled kernels; aggressive engines pre-tune them per model (chapter 18).
  • Threadgroup / SIMD shape — Apple GPUs execute in 32-wide SIMD groups within threadgroups; matrix kernels tuned to this shape (as MLX's are) run much faster than naive ports.
  • Unified memory addresses — GPU kernels read the same virtual addresses as the CPU; no staging buffers, no copies. llama.cpp's Metal backend actually pays a small overhead emulating its CPU-oriented memory model, while MLX was designed around this hardware — a key reason MLX is faster (chapter 13).

Metal vs CUDA, honestly

CUDA has 18 years of kernel libraries, autotuning infrastructure, and community knowledge. Metal has fewer battle-tested primitives but one giant advantage: zero-copy access to 128GB of RAM. For bandwidth-bound single-stream decode, Apple's design is genuinely competitive — and less explored, meaning more room for new work (your motivation, presumably).

09Quantization — shrinking the weights

Weights are trained at 16-bit precision (fp16/bf16). Quantization stores them at lower precision. Since decode speed = bandwidth ÷ bytes, halving bytes directly doubles decode speed. This is the biggest lever you control.

How it works

Take a group of weights (e.g. 32 numbers), record the group's min/max or a scale factor, then store only small integers (4 bits → 16 possible values) plus the shared scale. Dequantize on the fly during compute. Modern schemes add small correction blocks (GGUF's super-blocks, e.g. Q4_K_M uses 6-bit scales for its 4-bit values) to preserve accuracy.

The formats you'll encounter

FormatBits/weight7B model sizeNotes
FP16 / BF1616~14 GBFull precision; rarely worth it locally
Q8_0 / int88.5~7.5 GBVisually lossless
Q4_K_M / int4~4.8~4.4 GBThe sweet spot — ~3% quality drop, ~75% smaller
Q3_K_M~3.9~3.3 GBNoticeable degradation on hard tasks
Q2_K~3.0~2.7 GBLast resort; models get "weird"
NVFP4 (newer)4~3.7 GBHardware-friendly 4-bit layout, strong quality at this size

Rules that hold up in practice

  • Q4-ish is the default choice. Quality loss ~3%, speed ~2x vs fp16. Below Q4, quality falls off a cliff; above Q5, you pay for precision you can't perceive.
  • Prefer a bigger model at Q4 over a smaller model at Q8. A 14B at Q4 beats an 8B at Q8 on almost every task, at the same memory cost (~8GB either way).
  • MoE models tolerate quantization better — sparse routing means any individual weight matters less.
  • Never quantize embeddings/output head aggressively — they touch the whole vocabulary; most formats keep these at higher precision.

Choosing your model size in one step

Take your RAM budget (chapter 7). Model at 4-bit should be ≤ budget − KV cache for your context length. Then pick the largest quality model that fits, because at 4-bit, decode speed is inversely proportional to size and there's no way around that tradeoff. Speed per token is fixed by size; the only free speedups are quantization (already spent), speculation (chapter 11), and a faster engine (chapter 18).

10Sampling — turning logits into tokens

The model outputs a probability for each of ~100k–200k vocabulary entries. Sampling chooses which one to take. It's negligible compute, but it shapes output quality, so know the knobs:

ParameterWhat it doesSensible default
temperatureScales the distribution; low = deterministic, high = creative0.7 (chat), 0–0.2 (code/facts)
top_p (nucleus)Keep only the most probable tokens summing to p0.9
top_kKeep only the k most likely tokens40–50 (or skip if using top_p)

One relevant performance note: the output head (the final matrix projecting to vocabulary size) is expensive for large vocabularies — it's a 1×V multiplication against a huge matrix every step. Engines with fused/delayed output-head kernels or sampled-every-k optimizations save real bandwidth, and it's another place where engines differ.

11Speculative decoding — the near-free lunch

The core insight: during decode your GPU is bandwidth-bound, with math units mostly idle. Speculative decoding spends that idle compute to amortize the bandwidth cost across several tokens.

How it works

Draft phase: a small "draft" model (e.g. 1B) guesses the next k=5 tokens ↓ cheap: 5 tiny forward passes Verify phase: the big model checks all 5 guesses in ONE pass ↓ costs same bandwidth as generating 1 token Accept phase: keep longest matching prefix + 1 corrected token Worst case: 1 token for 1 big pass (no loss) Best case: 6 tokens for 1 big pass (6x speedup on that step) Typical: ~2–3x overall

Verification is cheap because the big model can score k future positions in parallel in one forward pass (prefill-style, compute-bound, using idle math units). The draft model is so small its passes cost almost nothing.

Variants you should know

  • Classic two-model — small draft + big verifier. Requires a matched pair sharing a vocabulary.
  • Self-speculation / Medusa-style — the big model has extra small heads that predict several tokens ahead from its own hidden state. No second model needed.
  • Draft-tree speculation — draft a tree of candidate continuations, verify as a batch. More acceptance, more complexity.
  • Sparse self-speculative decoding (2026 research) — use a subset of the model's own layers as the "draft" path. Very promising on memory-constrained Macs since there's no extra model resident.

Why this is the biggest untapped local win

Speculation gives ~2–3x on decode, composes with quantization (draft model can be tiny at 4-bit), and is nearly free in hardware terms — yet most casual local users never enable it, and most engines implement it poorly. An engine architected around speculation (co-resident draft, automatic draft selection, tree verification) is a legitimate way to beat the default experience. The catch: it helps most when the draft and main model "think alike" — acceptance rate depends on task; expect ~50–70% acceptance for well-matched pairs.

12Batching, prefix caching, MoE & friends

Continuous batching

Serving many users? Interleave: as one request finishes prefill, slot another in; decode steps of different sequences proceed together. One batched decode pass streams weights once for all sequences — serving 10 users costs barely more bandwidth than serving 1. This is how datacenters get throughput. For a single local user it's irrelevant — but if you build serving infrastructure (agent swarms, app backends), batching on Mac with vllm-mlx is genuinely effective; the EuroMLSys 2026 paper measured 21–87% throughput gains over llama.cpp from batching + caching alone.

Prefix caching

Discussed in chapter 5; reiterating because agents make this matter: every time your coding agent appends to the same conversation, only the new suffix needs processing. Engines that detect and reuse shared prefixes turn multi-minute agent turns into near-instant starts. When choosing an engine, ask: "does it persist KV across requests with matching prefixes?"

Mixture-of-Experts (MoE)

MoE models (Mixtral, DeepSeek, Qwen3-35B-A3B, gpt-oss) contain many expert MLPs but route each token through only 1–2. Parameter count is huge (35B) but active params per token are small (3B). Effect on Mac: MoE decode speed tracks the active parameter bytes, so a 35B-A3B at 4-bit (~18GB) decodes at 3B-model speed (~2.5–3GB streamed/token → 40+ tok/s on Pro chips) while thinking like a 35B. The cost: all experts must fit in RAM. MoE is arguably the local-model architecture of 2025–26 because it converts capacity into quality without paying bandwidth for it.

Attention optimizations

  • FlashAttention — computes attention without materializing the full attention matrix, keeping tiles in GPU registers. Big memory savings at long context; both MLX and llama.cpp implement variants.
  • Sliding window / interleaved local attention — architectural, bounds attention cost for long contexts (chapter 5).
  • GQA — architectural, shrinks cache (chapter 3).

12bParallel & byte-level tokenization

One "everything else" topic deserves its own chapter: the tokenizer itself. It's invisible in every benchmark because it doesn't touch decode — but at long contexts it quietly dominates time-to-first-token, and there's an active research wave attacking its sequential nature.

First, why this doesn't affect decode

During decode, tokens already exist as integers; the model emits an id, and incremental detokenization (id → text fragment) is microseconds. Decode performance is untouched by tokenizer design. The problem is prefill: BPE tokenization is left-to-right greedy longest-match against a merge table — inherently sequential, single-core. Tokenizing a 4MB document takes ~0.8s with the Llama 3 tokenizer; for an agent re-ingesting a 200k-token transcript each turn, that's 100ms–1s of pure TTFT overhead, paid every turn.

Priority check

Chat with short prompts: tokenizer cost ≈ nothing. Agents/RAG with long contexts: tokenization can be 10–50% of TTFT. It's a real win for the agent-workload engine — but it comes after the decode-kernel work, which is where the 2x lives.

Thread 1 — Parallel tokenization (keep BPE, remove the scan)

  • LoPT (ACL 2026) — lossless parallel tokenization. Chunk the text, tokenize chunks concurrently, then fix the one thing that can differ: a chunk boundary can split a potential merge. LoPT repairs boundaries via character-position-based token merging + dynamic chunk-length adjustment. Output is bit-identical to serial tokenization; several times faster.
  • ParallelTokenizer (OpenLLMab, 2024) and Charles Xu's 5.5x faster HF tokenizers — segment text at byte-safe boundaries: a cut is safe if the byte before it maps to itself, so no normalizer offset can lag across the boundary. Word ids are rebased per segment; post-processing runs once on the concatenation.
  • The transferable insight: chunk boundaries are safe only at byte-self-mapping positions. Get that check right and parallel tokenization is lossless, trivially — and embarrassingly parallel (you could even run it on the GPU that's otherwise idle during prefill).

Thread 2 — Tokenizer-free / byte-level models

  • Byte Latent Transformer (Meta, 2024) — dynamic byte patches, no vocabulary at all.
  • MambaByte (2024) — bytes at sequence-model scale via state-space models, avoiding the quadratic attention that historically forced tokenization onto transformers.
  • H-Net / Bolmo (2025–26) — the model learns its own chunk boundaries (dynamic chunking); non-causal one-byte-lookahead routers recover near-perfect alignment to classic token boundaries.
  • zip2zip (2025) — adaptively merges tokens based on context; MrT — soft gating to shorten sequences at inference.

Status check (Nature, 2026): byte-level LLMs still haven't displaced subword tokenization in any leading model — the efficiency–quality Pareto frontier hasn't tipped. But it's no longer fringe.

Thread 3 — The sleeper connection: byte interfaces × speculative decoding

This is the one that matters for an engine that beats MLX. Classic speculative decoding requires the draft model and verifier to share a vocabulary — which locks you into matched model pairs. Byte-level output interfaces change that:

  • Byte-Level Distillation (BLD) — converts a teacher's token distribution to byte probabilities (Vieira et al., 2025 approximation) and attaches a byte-level decoder head to the student. Distillation across incompatible vocabularies, no alignment heuristics.
  • ByteSampler (2025) — derives byte-level output distributions from any token LLM at inference, without retraining.

The implication: a byte interface could let you pair any small draft model with any large verifier regardless of tokenizer — unlocking draft/verify combinations that vocabulary matching forbids. That's a speculative-decoding moat, on top of the 2–3x the technique already gives (chapter 11).

Where this fits in the engine roadmap

Phase 4½ material: parallel tokenization (LoPT-style, GPU-parallel) for fast agent prefill, and a byte-level output interface to make speculative decoding tokenizer-agnostic. Both attack TTFT/agent latency — the same metric as prefix caching — rather than decode bandwidth.

14MLX internals — why it wins

Three design choices explain MLX's speed on Apple Silicon:

  1. Lazy evaluation with graph fusion. MLX doesn't execute ops as you call them; it builds a graph, then runs it — and can fuse consecutive elementwise ops (norms, activations, residuals) into single kernels. Fewer kernels = less Metal launch overhead = higher fraction of time spent reading weights (which is what decode needs).
  2. Unified-memory-native layouts. Tensors are allocated in shared memory from the start. No CPU↔GPU staging, no copies at boundaries. llama.cpp must bridge its CPU-centric memory model to Metal; MLX never had the seam.
  3. Hand-tuned Apple-GPU kernels for the hot ops: GEMV/GEMM (matmuls), quantized dequant-matmul fusion, attention. The quantized-matmul kernels in particular dequantize inside the matmul kernel, avoiding a separate pass over weights.

Where MLX is weak

  • General-purpose kernels. Its kernels fit all shapes and models; they are not auto-tuned to your specific chip + model + workload (more in ch. 18).
  • Decode is still ~60–75% of bandwidth ceiling — kernel launch overhead and imperfect weight-streaming schedules remain.
  • Speculative decoding exists but isn't first-class — no automatic draft-model management, limited tree speculation.
  • Serving features (batching, paging) arrived only via the vllm-mlx layer, not core MLX.

15llama.cpp internals — the reference engine

Even if you never run it, understand it — the whole ecosystem's vocabulary (GGUF, -ngl, Q4_K_M) is llama.cpp's.

Architecture

  • GGML — the tensor library underneath: quantization formats, SIMD/CUDA/Metal backends, graph execution.
  • GGUF — the single-file model container: weights + tokenizer + metadata in one mmap-able file. mmap means the OS pages weights in on demand — instant startup even for huge models.
  • The graph — each forward pass builds an explicit computation graph, then executes kernel-by-kernel. Less fusion opportunity than MLX's lazy approach; more portability.

The flags that matter

llama-server -m model.gguf \
  -ngl 999          # offload ALL layers to GPU (the flag everyone forgets)
  --flash-attn      # fused attention: big win at long context
  -c 8192           # context size — set to what you NEED; KV cache eats bandwidth
  -ctk q8_0 -ctv q8_0  # quantize the KV cache (halves its bandwidth+memory)
  --mlock           # pin weights in RAM, avoid paging
  --parallel 1      # raise only if serving multiple users

Common self-inflicted wounds

  • Forgetting -ngl and running on CPU (speed: ~1/10th).
  • Setting context to 128k "to be safe" — silently consumes 10s of GB and slows every token.
  • Leaving fp16 KV cache at long contexts when q8 costs nothing in quality.
  • Judging quant quality from one cherry-picked answer — use perplexity on a real corpus or a task suite you care about.

Methodology rules

  1. Fix everything but the variable. Same model file, same context, same quant, same prompt set. Change one thing.
  2. Warm up. First run includes shader compilation and cache cold-start; discard or average after warmup.
  3. Measure mid-generation, not averaged-with-prefill. A long prefill destroys decode averages.

The M5 generation (2025–26): matrix units inside the GPU

The M5's headline change for inference is not bandwidth — it's that every GPU core now contains Neural Accelerators: dedicated matrix units optimized for low-precision math (FP16/BF16, and crucially 4-bit float formats). Apple's own MLX benchmarks (prompt size 4096) show what this buys:

The ANE question, settled (for now)

A common 2026 question: "why don't runtimes use the Apple Neural Engine?" The answer (Contra Collective's M5 Max teardown): the ANE executes compiled, fixed-shape graphs and has no practical mechanism for a live, growing KV cache or dynamic sequence shapes — which is what generation fundamentally is. Apple's own on-device Apple Intelligence models are ANE-shaped, but every major open runtime (MLX, llama.cpp, Ollama) uses the GPU. The M5 change is telling: instead of pushing inference to the ANE, Apple put ANE-style matrix units inside the GPU — meeting the runtimes where they live. This is also why MLX now requires macOS 26.2+ to use the Neural Accelerators.

18Frontier: the 4-bit float war — MXFP4 vs NVFP4 vs TurboQuant

The biggest quantization story of 2026: integer quantization is being displaced by 4-bit float formats — and models are now being trained natively at 4 bits.

The two formats

Both store weights in the E2M1 float element type (4 bits: 1 sign, 2 exponent, 1 mantissa — values like ±0.5, ±1.0, ±1.5, … ±6.0). The difference is how each small group of weights is scaled:

MXFP4 (OCP standard)NVFP4 (NVIDIA)
Block size32 weights16 weights
Scale typeE8M0 FP8 — powers of two onlyFull FP8 (E4M3) — any value in range
Scale overhead0.25 bits/weight0.5 bits/weight
BehaviorSnaps block scale to nearest power of 2 — cheap hardware, wasted range when a block's dynamic range is awkwardTracks local dynamic range tightly — measurably better accuracy where int4 hurts

The 2026 state of the war

  • Frontier models are now trained quantization-aware at 4 bits. OpenAI's gpt-oss-20b/120b bake MXFP4 into training — over 90% of their parameters (the MoE experts) are 4-bit by design, which is how the 120B fits on a single 80GB GPU. DeepSeek-V4 uses NVFP4's finer 16-value blocks for the same trick. QAT (quantization-aware training) at 4 bits is becoming the default, not a post-hoc hack.
  • MXFP4 is catching up. A 2026 study (arXiv 2603.08713) shows enhanced MXFP4 strategies cut its accuracy loss by 62%, closing the gap to NVFP4 from ~10% to <1% on average — same bit budget, near parity.
  • On Apple Silicon, both work — and M5 makes them fast. The M5's Neural Accelerators handle 4-bit float natively; MLX supports MXFP4 and NVFP4 on macOS 26.2+. NVFP4's finer scaling is a real accuracy win on dense models where 4-bit int visibly degrades.
  • llama.cpp and vLLM both support the formats (NVFP4 also via Marlin-style kernels on NVIDIA).

TurboQuant-MLX — the wildcat entrant

April 2026: TurboQuant, adapted to MLX, reported usable 2-bit quantization on dense 1B–7B models (where standard affine quantization collapses), and — more dramatically — a 122B model compressed to run at 44 tok/s on a 64GB Mac (M4 Max), with quality claimed to beat standard 4-bit. Zero training data required. Treat with benchmark-before-belief caution, but it signals the new frontier: the interesting question is no longer "4-bit vs 8-bit" but "how much better can clever scaling + error feedback get than naive block quantization at any bit width."

What changed for you

The chapter 9 table (Q4_K_M ≈ 4.8 bpw) is now the integer baseline. The 2026 decision tree: prefer native QAT 4-bit float models (gpt-oss-style MXFP4, NVFP4-quantized Qwen/DeepSeek distills) when they exist for your model — they're trained for the format and outperform post-hoc int4. On M5+, these formats also get hardware acceleration. GGUF's Q4_K_M remains the compatibility floor; float-4 is the quality ceiling at the same size.

Vegas / SpecAttn: verification-guided sparse attention (Feb 2026)

The cleverest 2026 idea: a draft model's biggest weakness is low acceptance rate, and a big cause is drafting over a huge, noisy KV cache. Vegas/SpecAttn makes verification itself identify the critical KV entries (as a byproduct of the batch-verify pass), then drafts attending only to those. Results: 1.25–2.81× decoding throughput over default vLLM, 1.15–1.29× over prior sparse-attention self-speculation methods, and — importantly for Macs — gains scale with context length, exactly where decode hurts most. Training-free, implemented in vLLM as plug-and-play.

What 2026's systematic benchmark found

SpecDecode-Bench (2026) evaluated five variants (n-gram, EAGLE, EAGLE-3, draft-model, MTP) across four models and six workloads. The takeaway that matters: no single speculation strategy wins everywhere — acceptance rates are workload-dependent (extractive tasks love n-gram; creative text defeats all drafting), so the winning engine is one that runs multiple drafters and adapts. This is a direct argument for the "speculation as default path with adaptive enable" design in chapter 23.

Why this is the Mac's killer optimization

Self-speculative methods need no second model in RAM (the Mac's scarce resource) and consume idle math units (the Mac's abundant resource during decode). Vegas-style sparse attention + self-speculation is essentially purpose-built for the unified-memory bandwidth-bound regime — it cuts the KV reads per draft step (fewer bytes) while filling the idle compute. If you build one optimization after fused kernels, build this.

20Frontier: distributed Macs — RDMA over Thunderbolt

The October 2026 story that changes "the ceiling" from one machine's RAM to your whole desk of machines.

What Apple shipped

MLX 0.21 brought real distributed inference primitives; macOS 26.2 added RDMA over Thunderbolt 5; and Apple's JACCL library provides collective communication (send/receive/broadcast/reduce — an MPI-like surface) over that transport with minimal CPU/OS overhead. WWDC26 sessions (232 & 233) documented the full path: mlx.distributed.init(backend="jaccl"), sharded_load() with pipeline/tensor groups, mlx.launch with a generated hostfile, and MLX_METAL_FAST_SYNCH=1 (faster GPU↔CPU sync — critical because compute runs on GPU while communication runs on CPU).

# WWDC26-style minimal cluster launch
mlx.distributed_config   # generates the hostfile (hostnames, IPs, RDMA devices)
mlx.launch --hostfile hosts.json --auto-setup \
  -m mlx_lm.server --model moonshotai/Kimi-K2.6   # auto-sharded across nodes

# inside your code, the API surface:
group = mx.distributed.init(strict=True, backend="jaccl")
model, tokenizer = sharded_load("model-id", pipeline_group, tensor_group)

The measured numbers (Apple ML Research, October 15, 2026)

  • Single-machine M5 Ultra vs M3 Ultra on Qwen3.8-27B BF16 (8k-token prompt): decode 19.7 vs 12.5 tok/s (1.58×), TTFT 4.1s vs 18.2s (4.4×) — the Ultra tier converts bandwidth directly into prefill and large-model capability.
  • Two Mac Studios (512GB each) on one TB5 cable: Llama 4 Maverick (~400B MoE) in 4-bit, ~220GB sharded by expert parallelism — 110GB resident per node.
  • Four-node clusters: up to 3× inference throughput (WWDC26); ~600 tok/s aggregate fine-tuning in the demo; Apple cites frontier-class distributed runs across four 512GB Mac Studios "exceeding human reading speed."

Why this architecture works (and when it doesn't)

  • Expert parallelism is the MoE cheat code. MoE models shard naturally: each Mac holds a subset of experts, tokens route to whichever node owns the needed expert. Communication is small (routing decisions + activations), memory per node is 1/N of the model. This is how ~400B–2.8T-parameter open models become desk-runnable.
  • Tensor/pipeline parallelism covers dense models: layers split across nodes, each decode step incurs cross-node sync — RDMA-over-TB5 makes that cheap (~80Gb/s per cable, µs latency), which is why "up to 3× with four nodes" is realistic rather than fantasy.
  • vs NVIDIA's answer: against a single DGX Spark, an M5 Ultra decodes a 27B dense model ~4× faster (bandwidth wins). Cluster two DGX Sparks over GX10 networking and the comparison flips — for concurrent multi-user serving, not single-stream decode.

The honest costs

  • Decode per token in pipeline-parallel mode is still bound by the slowest path through the chain — distributed adds capability (bigger models), and throughput, more than single-stream decode speed.
  • You need macOS 26.2+, MLX ≥ 0.21, Thunderbolt 5 ports on both machines (a 10GbE network is the fallback and is slower).
  • Sharding config (pipeline vs tensor vs expert groups) is still manual for custom strategies — the CLI auto-shards, the Python API exposes raw control.

Strategic significance for "beating MLX"

Distributed unified memory resets the roofline game: your "bandwidth" budget becomes per-node bandwidth plus interconnect bandwidth, and expert-parallel MoE sharding minimizes cross-node traffic. An engine built on MLX's distributed primitives — or better, one that improves the cross-node scheduling (batch expert routing to reduce sync count) — competes in a space where MLX itself is only months old. Nobody's optimized yet. Greenfield.

21dThe model floor — how small can useful models go?

The physics floor: knowledge capacity per parameter

"How much do language models memorize?" (Morris et al., 2025) established a usable conversion: a trained transformer stores roughly ~3.6 bits of knowledge per parameter.

knowledge capacity ≈ 3.6 bits × params 100M params ≈ 45 MB of facts (a short book + grammar) 1B params ≈ 450 MB (a slice of Wikipedia) 7B params ≈ 3.2 GB (broad Wikipedia + code + common sense) 70B params ≈ 30 GB (long-tail knowledge)

This is why sub-100M models can't chat usefully: it's a storage problem, not a training problem. English Wikipedia (~2.5B tokens of semantic content) already exceeds a 1B model's capacity. The floor for a fact-bearing general model is set by how much world knowledge the task demands.

  • Retrieval / tools — the conceptual lever: offload knowledge into context. A RAG-augmented 270M answers fact questions a bare 7B can't. RAG deletes the knowledge term from the floor, leaving reasoning + format, which fits in ~100M params.
  • Micro-MoE — LFM2.5-24B-A2B (24B knowledge / 2.45B active) points at 500M-total/30M-active experiments.

Bottom line: fluent language floor ≈ 1–10M (TinyStories). Working specialist floor ≈ 100–270M. General chat floor ≈ 2–3B at 4-bit — and it has moved down ~3× in two years purely via overtraining + distillation. The floor is only soft if you remove the knowledge requirement (RAG + tools).

21eWhere small models actually win

The ladder's floors matter less than this question: where do small models outperform — not just "acceptable," but actually better? There are five mechanisms, each producing a category of win.

Mechanism 1: The task is narrow, so the distribution is tiny

A model only needs to model the distribution of its task. Function calling from a fixed app schema, routing a support ticket into 12 queues, extracting dates and amounts from invoices — these have low-entropy output spaces that 100–270M params cover completely. FunctionGemma's 90% on app intents is the canonical result; the pattern repeats across routing/classification/extraction benchmarks, and a fine-tuned specialist regularly beats a general 70B on that task while using 1/300th of the compute.

Mechanism 2: The knowledge lives in the context, not the weights

RAG + tools delete the knowledge-storage term (ch. 21d). Given retrieved documents, a 1B can summarize and answer questions whose facts it could never store. This is why retrieval-augmented small models are the production pattern for private-domain Q&A: your corpus is the memory, the model is only the reader.

Mechanism 3: Latency and battery are the metric, not quality

Keyboard suggestion, smart reply, autocomplete, live transcription need sub-100ms responses; a big model can't compete because physics forbids it, not because it's dumber. Gemma 3 270M: 0.75% battery per 25 conversations; FunctionGemma does ~2,000 tok/s prefill on a Pixel 7. On the desktop equivalent: LFM2.5-24B-A2B at ~139 tok/s on M5 Max makes agent loops feel instant; Mellum2.1 (12B/2.5B) exists precisely as an IDE-sized completion specialist.

Mechanism 4: Privacy / locality requirements

When the data can't leave the device (health, finance, keyboard content), the smallest model that does the task adequately wins by default — it's not competing on quality, it's competing on "runs locally at all." This is Apple Intelligence's whole design: on-device 3B-class model handling most requests, deferring only hard ones.

Mechanism 5: Volume economics

2026's production reality (DeployBase, BentoML surveys): teams ship task-specific small models far more than general giants. A support bot processing millions of tickets doesn't need frontier quality per reply — it needs 95th-percentile quality at 1/50th the cost and 5× the speed. Small models win the unit-economics game structurally.

21iThe 500 tok/s horizon — where SLMs are heading

First: what 500 tok/s demands of on-device hardware

The roofline (ch. 4) makes 500 tok/s a specific claim, not a vibe:

500 tok/s needs: bandwidth ÷ bytes-per-token ≥ 500 M5 Max (614 GB/s) → ~1.2GB of weights read per token (≈1B dense at Q4) M5 Ultra (1.2TB/s) → ~2.4GB per token (≈2B dense at Q4) ...or ~4–8B total params at Q4 with ×2–3 speculative decoding ...or a MoE with ~1–2B ACTIVE params at Q4 (8B-A1B class)

So "500 tok/s on-device" defines a specific model tier: ~1–2B active parameters — dense SLMs or the new micro-MoE class. This is exactly why the 2026 model releases matter (LFM2.5-8B-A1B, Qwen3.5-A3B family): they are the first models architected for this threshold. LFM2.5-8B-A1B already serves at 335 tok/s API-side; on-device equivalents on M5-Pro-class silicon are the next step.

The capability unlocks at 500+ tok/s on-device

  1. Thinking becomes invisible. Reasoning models generate 2,000–50,000 tokens before answering. At 60 tok/s that's minutes of spinner; at 500 it's seconds — within Nielsen's ~1s flow threshold for short chains. The "AI pauses to think" interaction pattern becomes real-time. This is arguably the single biggest unlock: local models get the capability of reasoning models with the latency of small ones, because thinking tokens stop costing wall-clock time.
  2. Agentic loops with self-correction. A coding agent's value is proportional to iterations it can afford. At 500 tok/s + fast prefill, a local agent can attempt→fail→diagnose→retry ten times in the time one attempt takes today. On-device agents shift from "single shot, hope it's right" to "iterative until correct" — the quality behavior that makes cloud agents feel smart is mostly just iteration speed.
  3. Voice-native becomes the default interface. The full speech loop (VAD→ASR→LLM→TTS) is a pipeline of the ch. 21h specialists: Silero (2MB) + Parakeet (631MB) + SLM + Kokoro (160MB). At 500 tok/s the LLM leg of that loop costs ~10ms per response sentence — the whole loop fits inside conversational latency, and interruption (barge-in) works because the model can regenerate mid-sentence. Local voice assistants go from demo to daily-driver.
  4. Ambient & continuous AI. At 60 tok/s you can't afford to process a screen stream; at 500+, a permanently resident micro-VLM can describe/skim every screen change within a few percent of one core's budget. This enables the "computer that watches with you" category: meeting co-pilots, memory capture, proactive suggestions — the assumed-usage shift from you ask the computer to the computer participates.
  5. Local multi-agent swarms. Three concurrent agents at 500 tok/s = 1,500 tok/s aggregate — feasible only with batched decode (weights streamed once, ch. 12) plus a RAM budget for 3× KV. Claude-style "subagents" become a local pattern: a router SLM spawning task agents, specialists (ch. 21h) doing the heavy calls.
  6. The cascade collapses into one instant intelligence. Ch. 21e's router→specialist→generalist stack only feels good if the router answers in zero perceived time. At 500 tok/s for the 66M router, 100ms for the 3B, and streaming for the big model, the tiering disappears from the user's perception — privacy-preserving local AI finally has the speed to be the default path, with cloud as the escalation tier rather than the first call.
  7. Live-generated UI. An interface that streams UI code/text at 500 tok/s can render whole components as you watch. "AI-generated interface per query" goes from gimmick (too slow to stream) to viable interaction style.
  8. On-device self-improvement loops. Interactive-speed inference makes local RL-from-feedback and rapid LoRA personalization (ch. 14) practical — the model that adjusts to your writing/preferences in-session rather than overnight.

The hardware path to 500+ (2026 → 2028)

  • Now (M5 generation): Neural Accelerators + QAT 4-bit float + micro-MoE get a 1–2B-active model to ~150–300 tok/s on Max/Ultra chips. Speculation adds ×2–3 — 500 tok/s is a software milestone on 2026 hardware, for 1–2B-active models.
  • 2027 (LPDDR6 + PIM): JEDEC's LPDDR6 standard (published July 2025, updated spec in progress) brings 512GB densities and a narrower x6 interface; bandwidth +10–20%. The real prize is LPDDR6-PIM — compute inside the memory: Samsung's LPDDR5X-PIM demo (Hot Chips 2026) exposes 614 GB/s of bank-internal bandwidth to its compute units. PIM attacks exactly the roofline: decode stops being a data-movement problem when the MACs live next to the DRAM banks. The LP-Spec paper (arXiv 2508.07227) already co-designs speculative inference with PIM dataflows for mobile.
  • The compounding claim: bandwidth ×2 (LPDDR6) × PIM internal-bandwidth (614 GB/s bank-level) × speculation ×2–3 × micro-MoE active-params ÷4 ⇒ 500–1,000 tok/s on laptops, with 4–8B-A1B-class quality — roughly 2027–2028.

What doesn't change

  • TTFT becomes the whole game. Once decode saturates perception, the only latency users feel is prefill — which makes parallel tokenization (ch. 12b), prefix caching, and fast prefill kernels the highest-value engine features of the 500+ era, not decode.
  • Memory capacity still gates capability. 500 tok/s with a 2B model is speed without depth; the specialist-stack pattern (ch. 21h) exists precisely because ambient SLMs need surrounding generalists.
  • Bandwidth is still the wall — PIM just moves the wall. The roofline survives; the constant changes.

October 2026 reality checks on the MLX numbers

  • "Engine wins" are model-and-quant dependent: a 54-run measurement found MLX +41% on dense 27B at 4-bit, parity at 8-bit, and Ollama +22% on a 30B MoE (83 vs 68 tok/s). Benchmarks on your model, not vibes.
  • UI tok/s ≠ wall clock: on long-context workloads MLX's reported decode speed can hide a prefill wall (one documented case: 51 tok/s reported, ~3 tok/s effective on an 8.5k-context response; another: a 40k-token file sipping 10W for 3.5 minutes before the first token). Measure end-to-end.
  • Rapid-MLX (open source, Apache 2.0): an MLX server claiming up to 4× over mlx-lm on the same weights, with a verified MTP/speculative lane at 2.02× sustained (19.4 vs 9.6 tok/s on a 122B mixed-precision artifact) — evidence the speculation-first thesis of ch. 23 is already paying out in the wild.

The heading, in one paragraph

SLMs are heading toward being always-resident infrastructure rather than invoked applications: a 1–2B-active model (or its specialist cascade) that thinks interactively, answers in voice, watches ambient streams, and orchestrates tools — with the generalist escalating behind it. 500 tok/s on-device is the threshold where local AI stops being a cheaper cloud substitute and starts being a different product: the computer gains a continuous intelligence layer that cloud economics could never give you (privacy, latency, simultaneity). The software problems (fused kernels, speculation-first serving, cluster scheduling, prefill caching) are the ones this guide's ch. 22–23 catalog; the hardware ones (LPDDR6-PIM) are already scheduled. The gap between "assumed usage" of 2023 AI (ask, wait, read) and 2028 AI (delegate, converse, cohabit) is, almost entirely, a tokens-per-second curve.

21jDiffusion language models — the agent motor

For chat, diffusion is a speed story with a quality asterisk. For agents, the trade inverts: the weaknesses matter less, the strengths matter more, and the metric that was irrelevant becomes the whole game.

Quick primer

Autoregressive (AR) generation is a typewriter: token 50 can't exist before 49; every commitment is permanent; errors cascade forward. Diffusion generation is an editor: start with a block of blanks/noise, denoise all positions in parallel, revising any token at any step. Cost model: steps × full-weights-read ÷ bandwidth, amortized across the whole block — short generations favor AR, long structured blocks favor diffusion.

The state (October 2026)

  • Mercury 2.5 (Inception, Sept 2026): 1,100+ tok/s in production — "fastest reasoning model in production anywhere"; Mercury 2 ties GPT-5 Mini on AIME; Mercury Coder up to 10× faster than speed-optimized AR with comparable code quality.
  • Quality: competitive at the mid tier (Haiku-class); composite scores in the 40s vs frontier AR's 60s–70s. Parity not established. Independent guidance: keep an AR fallback for requests where diffusion underperforms.
  • Reasoning debate: The Flexibility Trap + Thinking Out of Order (Jan 2026) argue arbitrary-order generation decouples output order from reasoning order — a structural limit for long chains. The counter-case: built-in error correction (revise early mistakes instead of cascading them), and post-trained smaller DLMs beating larger AR models on math/logic.
  • Open weights exist: LLaDA-8B/V, Dream-7B, MDLM, DiffuLLaMA, DiffusionGemma, plus the 2026 distillation line (d3LLM pseudo-trajectory distillation, Efficient-DLM, AR-MAP — AR models as implicit diffusion teachers).

Why agents change the verdict

1. Agents are loops; speed multiplies the loop budget

An agent's effective intelligence is proportional to the iterations it can afford: attempt → observe → diagnose → retry. Inception's own product framing: "fast enough to run a hundred times per query." A diffusion model generating 10× the tokens per second converts directly into 10× the agent's per-turn iteration budget — the same mechanism that makes cloud agents feel smart, but paid in FLOPs instead of dollars.

2. Agent outputs dodge the flexibility trap

The anti-reasoning critique targets long narrative chains where order encodes logic. But an agent's per-step output is a short, structured block — a JSON action, a tool call, a summary — where order carries little meaning and any-position revision is pure upside. The trap binds where diffusion is weakest (long prose reasoning) and relaxes exactly where agents generate most of their tokens.

3. Parallel rollouts are a native operation

Sampling k candidate futures and picking the best (self-consistency, best-of-N, tree search) is how frontier agents actually reason well. For AR models each rollout is a separate sequential generation — k× the cost. Diffusion generates k blocks in one parallel batched pass. Planning-by-simulation goes from an expensive pattern to a cheap primitive. This is the deepest agent-relevant difference, and it compounds with #1.

4. Long horizons without KV-cache drag

AR agents accumulate a KV cache that grows all session long, slowing and eventually destabilizing (ch. 5). Diffusion blocks are regenerated per step; there's no quadratic attention drag on session length, and block-level regeneration is a natural context-compression mechanism. For 200-step autonomous tasks, that's a structural advantage, not a tuning knob.

5. Embodied agents already validate this

The strongest evidence is from vision-language-action models: LLaDA-VLA and dVLA (built on the multimodal diffusion backbone MMaDA) beat AR VLA baselines in both simulation and real-robot evaluations. In domains where the agent must perceive → decide → act in tight loops, diffusion backbones are already winning — robots are the canary for digital agents.

The architecture this points to

┌────────────────────────────────────────────┐ │ Pilot (AR reasoner): deep, sequential, │ │ plans, decomposes, judges, writes the hard │ │ reasoning — slow and expensive, runs rarely │ ├────────────────────────────────────────────┤ │ Motor (diffusion executor): fast, parallel, │ │ revisable — executes steps, formats tool │ │ calls, drafts k candidate actions, runs │ │ constantly at 1000+ tok/s │ └────────────────────────────────────────────┘ AR-MAP-style distillation between layers (AR teacher → diffusion student)

Two-layer AI: a sequential pilot for genuine reasoning, a parallel motor for everything an agent does that isn't deep reasoning — which is most of the token volume. The hybrid literature (Block Diffusion, causal AR-diffusion, d3LLM) is converging on exactly this inside single models.

What could still break it

  • Tool-call faithfulness: mid-tier quality means schema violations and hallucinated arguments — agents are the least forgiving consumers of output errors (a wrong click is a state change).
  • Long-horizon coherence: the demo-vs-scale reliability question is open (Mercury 2.5's own coverage flags it); plan AR fallbacks.
  • Local tooling: no mature MLX/llama.cpp dLLM path yet; open dLLMs run in transformers/vLLM-class stacks — an engine opportunity, not a capability.

The engine-opportunity note

llama.cpp supports Dream-class models via llama-diffusion-cli, but there is no MLX diffusion path — no fused Metal denoising kernels, no parallel-block batching, no MLX-native RND1. A compute-bound dLLM runtime on Apple Silicon (ch. 21j's "escape from the roofline") is unbuilt. If the AR engine race (ch. 23) is a 20–40% game, a native dLLM runtime is a 2–10× game on the hardware metric that matters (idle FLOPs), against almost no competition.

Can MLX + diffusion hit 500 tok/s on an M4? The arithmetic

Diffusion throughput has two regimes: Large block (compute-bound): throughput ≈ AR-prefill-rate ÷ steps(S) M4 Max 7B-class Q4 prefill ~800–1,300 tok/s Dream default (S≈32–64) → ~10–40 tok/s today Small block (weight-stream + compute mix): t_step ≈ max( W/bandwidth , 2·P·L/FLOPS ) M4 Max, Dream-7B Q4 (W=4.3GB): weight-stream ≈ 8ms/step L=64: compute ≈ 25–30ms/step (compute-bound) S=4 → 64/(4×28ms) ≈ ~570 tok/s — arithmetic says YES S=8 → ~285 tok/s Verdict: the M4 Max silicon permits 500+ tok/s diffusion decode for 64–128-token blocks at S≤4–8. What doesn't exist yet: (i) an MLX-native dLLM runtime with fused denoising kernels, (ii) an open few-step DISTILLED dLLM (Mercury's trick is distillation, not architecture), (iii) instruct quality at S=4. All three are open projects; none is blocked by physics.

The build that gets there: MLX runtime for Dream-7B/RND1 (fused batched-denoising Metal kernels, shared-computation caching across steps) + few-step distillation on top (d3LLM-style pseudo-trajectory) + short-block serving for agent-action workloads. Expected: 300–700 tok/s on M4 Max for 64–128-token outputs, 2× that on M5 Max — the agent-motor of ch. 21j, built on hardware you can buy today.

The future-of-AI synthesis

For chat, diffusion competes on speed and loses on ceiling. For agents, diffusion is plausibly the right substrate for the token-volume layer: loops, rollouts, structured calls, revision — the parts of agent work that are motion rather than thought. Combined with ch. 21i's threshold analysis, the 2027+ local stack takes shape: an always-resident diffusion motor (compute-bound — finally using the Mac's idle FLOPs, no KV drag, 500–2,000 tok/s) orchestrated by a small AR pilot, escalating to a frontier generalist for the rare deep-reasoning step. The roofline guide (ch. 4–5) describes the AR world; a compute-bound dLLM path is the first genuine escape from it — and the M5's Neural Accelerators exist almost precisely for that workload.

21kThe missing-unlock audit — what this guide almost missed

Confession-as-method: chapters 4–23 optimize one thing — how fast you stream autoregressive weights through memory. The diffusion chapter (21j) exposed the blind spot: bigger unlocks change what generation is, who does the computing, or where capability comes from. Here's the full audit.

A. Hybrid state-space architectures — the KV-cache-free AR world

The miss: the guide treats the KV cache as a fact of life (ch. 5). It isn't — it's a property of softmax attention. Linear-attention and state-space models (Mamba, RWKV, gated delta nets) carry a fixed-size recurrent state: O(1) memory per token, no cache, constant decode cost regardless of context length.

  • Proof it's real: Liquid's LFM family (LFM2, LFM2.5) is built on conv+SSM hybrids — and ch. 21h's speed champions (LFM2.5-24B-A2B at 139 tok/s on M5 Max) are fast partly because of this. Qwen3-Next-class hybrids (gated delta net layers + a few full-attention layers) validate the recipe at frontier scale.
  • Why it's an agent unlock: ch. 21j's "no KV drag at step 200" is exactly what these give natively — 10k-token agent sessions cost the same as 100-token ones. For always-resident ambient models (ch. 21i), fixed state = fixed RAM = the only architecture that lets a SLM run 24/7 without cache management.
  • Local status: llama.cpp and MLX support the Mamba/RWKV families; hybrid support is younger. An MLX-native fused recurrent-state decode kernel is another unbuilt, low-competition target.

B. Mixture-of-Depths — compute routing per token

The miss: the guide quantizes weights (ch. 9) but never routes tokens. Mixture-of-Depths lets each token skip layers via a learned router — most tokens use ⅓ of the network, hard tokens get everything. Documented: ~2× FLOP reduction at no quality loss on standard benchmarks.

  • Synergy: pairs with early-exit self-speculation (ch. 19) — MoD is "LayerSkip but learned and per-token." On Apple Silicon, skipped layers = unstreamed bytes = direct roofline relief during decode.
  • Agent angle: an agent's tokens are wildly heterogeneous (boilerplate JSON vs critical reasoning) — uniform compute is the waste MoD deletes.

C. Recurrent depth / latent reasoning — capability without capacity

The miss: the whole SLM thesis (ch. 21c–21d) assumed capability scales with parameters. Recurrent-depth models break that: a small block is looped k times before emitting, converting depth-recycling into test-time compute. A ~3.5B recurrent-depth model demonstrated latent reasoning approaching far larger dense models — computationally ~50B-class, memory-wise 3.5B-class.

  • Why it's the SLM thesis's best ally: it's the architectural version of "think longer, not bigger" (ch. 21i unlock #1). The knowledge floor (ch. 21d, 3.6 bits/param) still holds — but reasoning decouples from knowledge, and only reasoning needs the loop. A specialist with retrieval (ch. 21e mechanism 2) plus recurrent depth is a genuinely new point on the size↔capability frontier.
  • Cost: each loop = one full weights pass — it converts RAM savings into time, exactly the trade 500+ tok/s makes affordable.

D. Mixture-of-Agents — swarm beats monolith

The miss: the guide's cascade (ch. 21e) is serial escalation. Mixture-of-Agents is parallel: several small models answer independently, a synthesizer combines them — documented to beat GPT-4-class outputs using mid-tier models in earlier research, and it keeps working in 2026 benchmarks.

  • Local economics: cloud pays per token for N models; a Mac pays one-time RAM for co-resident weights. Ch. 12's batching streams weights once for all sequences — a 4×N-agent swarm on a 128GB Mac is RAM-feasible and bandwidth-shared. The cloud can't afford to run MoA at scale; a Mac Studio barely notices.
  • Diversity bonus: independent small models disagree usefully — disagreement is the signal the synthesizer exploits; a single big model has no such signal.

E. Test-time compute on small models — the budget-forcing synergy

The miss: ch. 21i treated speed as the unlock. The flip side: s1-style budget forcing — a small model that thinks 8× longer closes much of the gap to bigger models on reasoning. Speed and size trade directly: at 500 tok/s, a 3B thinking 8× is faster than a 27B thinking 1×. Speed is a capability multiplier, not just a UX metric.

F. The Metal kernel toolchain — the leverage nobody's using

The miss: ch. 18–23 assumed you write Metal shaders by hand. The 2026 toolchain exists and is underused: Triton-on-Metal ports, Mojo/MAX (Modular's stack compiles to Metal), tinygrad's Metal backend, plus evidence the gap is real — Rapid-MLX (open, Apache 2.0) claims up to 4× over mlx-lm on the same weights with a verified 2.02× speculative lane, and community engines (Lithos) claim to beat MLX outright on supported chips. The lesson: MLX's lead is an engineering margin, not a wall — and the tooling to attack it finally exists.

G. The small stuff, honestly ranked

  • Weight streaming from NVMe — mmap'd tiers beyond RAM (~40–60 GB/s on M4-class SSDs): ~1/10th of bandwidth, but it's "models 2× your RAM" capability. Extension, not unlock.
  • Radix-tree KV sharing (SGLang's trick) — prefix caching generalized across every request in a session; agent stacks should treat it as mandatory.
  • mlx-ane — a community effort to run MLX ops on the Neural Engine. Ch. 17 called ANE locked; this is the crack in that wall worth watching.
  • Apple Foundation Models framework — every Mac now ships with a free on-device 3B-class model API. It reframes "beating MLX": your engine competes against free and preinstalled, which changes the adoption bar from "faster" to "faster + more capable + still zero-config."
  • Browser-resident micro-models (WebGPU) — the 50–270MB specialist tier (ch. 21c) runs in a tab with zero install; a distribution unlock for the embedder/classifier floor.

The audit's meta-lesson

Every miss above shares one shape: we optimized the rate of a fixed process (stream AR weights), and the unlocks change the process — what a token costs (MoD, state-space), where capability lives (recurrent depth, retrieval), who computes (MoA swarms, pilot/motor), or what generation is (diffusion). The remaining AR-kernel work (ch. 23) is the reliable 20–40%; this chapter is the 2–10× list. Ranked by expected value for an Apple Silicon engine: A (state-space hybrids) → J/D (diffusion motor + MoA swarm) → B (MoD) → C (recurrent depth) → F (toolchain).

22The optimization playbook — ranked by leverage

What actually moves the needle, from most to least effort-to-payoff:

Tier 1 — free, do immediately

  1. Use an MLX-backed runtime. Ollama 0.19+, LM Studio with MLX, or mlx-lm. ~2x decode vs the llama.cpp path. Zero modeling skill required.
  2. Quantize to 4-bit. The default answer. 2x speed, 75% size, ~3% quality.
  3. Right-size context. Don't pay bandwidth for context you don't use.
  4. Quantize the KV cache (q8) at long contexts.

Tier 2 — config and workflow

  1. Pick MoE models for speed-per-quality when RAM allows (35B-A3B class).
  2. Exploit prefix caching — structure agent/system prompts to share long stable prefixes; keep conversations on one session.
  3. Close RAM-hungry apps during long generations; bandwidth is contested.
  4. Enable speculative decoding where supported — 2x-ish on top.

Tier 3 — engine-level engineering

  1. Fused persistent decode kernels (ch. 18).
  2. AOT kernel autotuning per chip/model.
  3. Paged KV + prefix cache server if serving agents/apps (vllm-mlx does this; go beyond it).
  4. Output-head optimizations for large-vocabulary models.

The compounding math

These multiply: llama.cpp default (say 25 tok/s on your machine) → MLX backend ×1.5 → 4-bit already assumed → speculation ×2 → prefix caching for agent turns ×5 TTFT → fused kernels ×1.3. Compounding turns "OK" into "feels native." Every factor above is real and demonstrated somewhere in 2025–26 literature.

The architecture of an MLX-beating engine

  1. One persistent fused decode kernel. Instead of ~dozens of shader calls per token (attention, norm, MLP, …), compile a single megakernel per model that executes an entire transformer block — or even all blocks — while keeping intermediates in registers/threadgroup memory. Weights stream through in a precomputed order that saturates the bus. Proof this direction works: megakernel approaches on NVIDIA (e.g. "Mirage/MP persistent kernels") hit 95%+ of bandwidth ceilings vs ~60% for conventional engines.
  2. AOT tuning pass. At model load (or download time), run a 10-second autotune: benchmark candidate kernel tilings on the user's actual chip with the model's actual shapes; cache the winner. This is what tinygrad does and what Metal's own shader pipelines make easy to piggyback on.
  3. Speculation as the default path. Ship with a tiny draft model auto-selected per main model; implement tree verification; measure acceptance and adaptively disable when acceptance is low. Users get 2x without knowing the word "speculative."
  4. Bandwidth scheduler. Treat decode as a scheduling problem: order the stream of (weights + KV pages) reads so every memory transaction is fully used. Prefetch next block's weights while current block computes — the GPU's idle math time is exactly enough to hide latency if scheduled right.
  5. Serving mode with paged KV + prefix reuse for agent workloads — where MLX core is weakest and vllm-mlx shows the demand.

The honest ceiling check: with weights at 4 bits and a perfect schedule, decode = bandwidth ÷ bytes. An engine can't beat that for single-stream dense decode — it can only reach it (MLX is 60–75% there), then go beyond it with speculation (amortizing bandwidth across tokens), MoE (smaller active bytes), and batching (sharing the stream). Any claim of "beating the roofline" without one of those mechanisms is a measurement artifact.

October 2026 addendum — what changed in this gap analysis

  • The hardware moved (ch. 17): M5's Neural Accelerators natively compute 4-bit float. The decode kernel you want to write can now use native MXFP4/NVFP4 matrix ops instead of integer-dequant-plus-FP16 — a new kernel-design axis that didn't exist on M4.
  • The model format moved (ch. 18): QAT-native 4-bit float models (gpt-oss, DeepSeek-V4, Nemotron) mean the "quantization overhead" of dequantizing inside the matmul partially vanishes — weights are the compute format.
  • The speculation frontier moved (ch. 19): Vegas/SpecAttn shows training-free self-speculation + sparse attention yields 1.25–2.81× and scales with context. It runs in vLLM but nobody has productized it on Apple Silicon — that's an open, named target.
  • The ceiling moved (ch. 20): RDMA/TB5 + JACCL turns N Macs into one memory pool. A new engine can treat the cluster as the target hardware from day one (expert-parallel MoE routing, batched cross-node sync) — a space where MLX is only months old and unoptimized.
  • What MLX still has that you don't: Apple's own M5-tuned kernels, the ecosystem, and distribution (Ollama/LM Studio). Beating it means being faster where it's weak: long-context decode (llama.cpp already eats MLX's lunch past ~40k), speculation-first serving, and cluster scheduling.
